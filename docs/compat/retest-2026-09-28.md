# Corpus re-test, 2026-09-28

Summary of the third compatibility run over the local third-party corpus (the same 15 packages and 390 skin `.ini`
files as on 2026-09-24, tested locally only, never distributed). Much changed since the last run: skin windows draw
into a bitmap of their own and keep pictures of the meters that did not change, legacy ANSI files are read in the code
page of the user's language, programs a skin runs that are Windows programs are logged instead of handed to Finder,
the Mac extensions (hardware sensors, glass, SF Symbols, weather) arrived, and many plugins changed. Human-readable
results: `docs/COMPATIBILITY.md` §12.

## What changed since 2026-09-24

- **Drawing path.** `--render` draws every meter; the kept-picture path of skin windows was checked with
  `--verify-drawing-cache` (updates, redraws without an update, mouse over and off, clicks, groups shown and hidden,
  an option set before the meter updates, image files replaced on disk, another backing scale): 0 of 390 skins
  differ from a full drawing in any of 11,609 frames. The check skipped the 13 skins that sit directly in their root
  config (CoreLoads, EasyInfo, HDD_Usage_Bars, Mini Weather, …) until the fix above; checked one by one first, then
  with the fixed folder walk, all pass.
- **Code page.** On this Chinese-language Mac every legacy file is tried in GBK first. None of the corpus's 162 legacy
  ANSI files decodes as GBK: in each of them a Western character (mostly a `·` separator, else a degree sign,
  ellipsis, bullet or accent) is followed by a space, quote or line end, which GBK does not allow after a lead byte,
  so all of them still read as Windows-1252; the English-language pass logs the same lines. A Chinese weather package
  outside the corpus (UTF-16 files, two skins, a Lua script and a web forecast) was rendered from a copy as well: the
  same with 0.1.0 and main, and with its forecast loaded (8 updates 2 s apart) the Chinese text is correct. UTF-16 and
  UTF-8 files do not depend on the code page.
- **Windows programs.** Enigma, HMNmeter2, Nelamint and PogPack ship Windows programs (`RainFile.exe`, `RainRGB4.exe`,
  `FindWOEID.exe`, `MAC.exe`, `.cmd` scripts, `StartOrb.exe`, `VoiceActivation.exe`, `EnigmaConfigure.exe`), and about
  40 action targets in the corpus name `.exe` or `.cmd` files. Such an action now logs "Cannot run … (Windows
  programs are not supported)" instead of making Finder say that macOS cannot open Windows applications. `--render`
  runs no mouse actions; the one program run at load (HMNmeter2's `wmic` through RunCommand) was already logged.
- **Sensors.** EasyInfo shows its CPU clock (3.5–4.5 GHz under load) and four core temperatures, Enigma's CoreTemp
  taskbar pieces show temperatures (0° in 0.1.0 and on 2026-09-24), FluentDash11 GPU no longer notes MSI Afterburner
  and shows the GPU clock, fan speed, temperature and GPU memory in use, FluentDash11 SYSINFO shows the clock in the
  CPU model line. The first sensor reading takes about 0.6 s, so FluentDash11 CPU's speed and temperature (and the GPU
  values) are still 0 after three updates 300 ms apart and filled in the slow pass.
- **Render environment.** `--render` now uses a fixed stand-in screen (1512 × 982 pt) instead of the Mac's own, so the
  Enigma Sidebar and Taskbar, which size themselves from the work area and screen width, changed size. Nothing else
  changed size.
- **Installer.** All 15 downloads install (with the code page of the user's language), as before; the installed copy
  renders with the same 11 notes, PogPack's `#MaxFileCount#` errors are gone, and its warnings (graphics and
  variables the raw folder cannot find) go from 124 to 12.

## Checked and not changed

The contact sheets of the 113 renders that differ from 0.1.0 show live data only (clocks, CPU, network rates, disk
free space, battery, Wi-Fi quality, uptime) apart from the sensor values and the two Enigma sizes above. Things that
look wrong in the renders but are the same in 0.1.0 and follow from the skins or the short test:

- FluentDash11 2- and 3-adapter network skins: the first adapter's labels overlap, because its value meters are empty
  strings (the adapter name comes from PowershellRM) and an empty String meter has no size, as in Rainmeter.
- FluentDash11 CPU Auto Core logs "Rectangle needs 4 numeric parameters": its background height comes from
  PowershellRM.
- Enigma Uptime prints "mm": the format ends in `m` and the meter adds `Postfix="m"` (skin bug).
- Enigma Process is empty in both short passes: its AdvancedCPU measures have `UpdateDivider=5`; with 8 updates a
  second apart it lists the top processes.
- Nelamint Player's play / pause picture path is mangled when the Skins folder's own path contains digits: its
  `Substitute="0":"#@#Play.png","1":"#@#Pause.png",…` also replaces digits inside the path it just inserted (pairs are
  applied in order; the test copies live under a numbered temporary folder, a normal Skins folder has no digits).

## Artefacts

Renders, logs, pair images and contact sheets stayed on the test machine (not in the repository). The Enigma Gallery
render shows a picture from the local Pictures folder, and the network skins show the machine's addresses, so none of
